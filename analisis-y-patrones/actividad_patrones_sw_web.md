# Actividad 1: Patrones de software para aplicaciones web
## Misión 1 — El portal no es un patrón

| # | Problema | Capa | Patrón/es | Por qué ese y no el vecino | Cuándo NO aplicaría |
|---|---|---|---|---|---|
| 1 | El chequeo de sesión, la bitácora y el encabezado HTML se copian en cada archivo de trámite | Políticas transversales | **Front Controller** (punto único de entrada) + **Chain of Responsibility** (pipeline de middleware) | No es Decorator: Decorator envuelve instancias de objetos de negocio para añadirles comportamiento de forma composicional y deliberada por el cliente; aquí el problema es un pipeline de petición que se aplica igual a todas las rutas, sin que nadie lo componga a mano caso por caso — eso es exactamente lo que resuelve un front controller con cadena de middleware | Si el portal tuviera dos o tres páginas nada más, montar un pipeline formal es sobre-ingeniería: bastaría una función `requireLogin()` llamada al inicio de cada handler |
| 2 | El kardex arma su tabla con SQL directo y las constancias repiten esas mismas consultas con otro formato | Datos | **Repository** (+ Query/Specification si las consultas varían mucho) | No es Active Record: Active Record está bien cuando cada entidad sabe guardarse/leerse a sí misma de forma simple; aquí el dolor es justo lo contrario, consultas compuestas reutilizadas por varios consumidores (kardex y constancias), lo que pide una colección de acceso a datos centralizada y con nombre de dominio (`obtenerCalificacionesDe(alumno)`), no que cada vista arme su propio SQL | Si solo existiera un único lugar que lee esas calificaciones, envolver la consulta en un Repository es una capa extra sin beneficio; un simple método privado bastaría |
| 3 | El pago acreditado dispara en el mismo hilo el alta de materias, el correo y el aviso a caja; si el correo falla a veces no se registra el alta, y el doble clic genera doble cargo | Aplicación/dominio | **Unit of Work** para la persistencia atómica del pago **+ Domain Events / Observer** para desacoplar los efectos secundarios, apoyado en una política de **idempotencia** (no es GoF, es una regla de diseño) | Aquí sí aplica distinguir Observer de Unit of Work, como pide el enunciado: Unit of Work garantiza que una operación (registrar el pago) se confirme o se revierta como todo — resuelve el doble cargo. Observer resuelve que varios interesados (control escolar, correo, caja) reaccionen a un hecho ya consumado sin que el éxito de uno dependa del éxito de otro — resuelve que un correo caído tumbe el alta de materias. Son problemas distintos y se necesitan los dos, no uno en lugar del otro | Si solo hubiera un efecto secundario obligatorio y no pudiera tolerarse inconsistencia eventual, ese efecto no debe ir a un Observer asíncrono: debe entrar en la misma Unit of Work. Observer es para lo que puede permitirse desacoplarse (correo, aviso a caja), no para todo |
| 4 | La app móvil y el kiosco de biblioteca deben ver el mismo trámite, pero uno pide JSON mínimo y otro HTML con escudo; hoy la app hace doce peticiones para pintar una pantalla | Presentación | **Facade** (una operación de aplicación que agrega lo que hoy son doce llamadas) + **Strategy/Presenter** para la representación de salida (JSON vs HTML) | No es Adapter: Adapter traduce una interfaz externa ajena para que calce con una interfaz que el cliente ya espera. Aquí no hay protocolo ajeno que adaptar, hay una operación propia mal fragmentada; el problema se resuelve unificando el caso de uso en una sola llamada (Facade) y luego decidiendo cómo se serializa esa misma respuesta (Presenter/Strategy de vista), no traduciendo un contrato externo | Si algún día ese "portal único" tuviera que exponerse tal cual a un tercero externo con su propio contrato ya definido (no controlado por la universidad), ahí sí tocaría Adapter; mientras JSON y HTML sean dos representaciones que la propia universidad diseña, es Facade + vista, no Adapter |
| 5 | El servicio del banco y el validador externo de CURP se caen seguido, y mientras no responden el estudiante ni siquiera puede consultar su kardex, que no depende de ellos | Integración | **Circuit Breaker** (+ Bulkhead para aislar el fallo) | No es Retry a secas: reintentar sin más solo demora el fallo y sigue bloqueando recursos; el síntoma descrito —que un colaborador caído tumbe una consulta que no depende de él— es acoplamiento de fallos entre subsistemas independientes, que es justo lo que Circuit Breaker + aislamiento de llamadas (bulkhead) cortan, dejando que el kardex responda aunque el banco esté caído | Si el kardex de verdad necesitara el dato del banco o del CURP para responder (dependencia real, no acoplamiento accidental), un circuit breaker no arregla nada: el problema sería de diseño de dependencias, no de resiliencia de red |
| 6 | Un proveedor propone Event Sourcing, CQRS, malla de microservicios y Redux global en el navegador para descargar una constancia en PDF (autenticar, leer un registro, generar un archivo) | — (meta-problema, ninguna capa lo pide) | **Ninguno adicional** — Controller + Service + Repository ya presentes en el framework bastan; principio **KISS/YAGNI** | No es que Event Sourcing/CQRS "estén mal": son la solución al problema de reconstruir estado a partir de un historial de eventos con lecturas y escrituras que escalan de forma muy distinta. Aquí no hay historial que reconstruir ni escritura que separar de lectura: es leer un registro y renderizar un PDF. Confundir "patrón de moda" con "patrón que aplica" es el error que esta fila señala | Aplicaría Event Sourcing/CQRS el día que el trámite necesite auditoría completa de cada cambio de estado del expediente con reproceso histórico y cargas de lectura/escritura muy distintas — no para descargar un PDF |

## Misión 2 — Una petición, varios patrones (`pagar la inscripción`)

Orden en que la petición `POST /inscripciones/pagar` atraviesa el sistema, sin capas vacías que solo delegan:

| Paso | Estructura | Mecanismo del framework | Patrón que realiza |
|---|---|---|---|
| 1 | Router/despachador (Express `app.post`, rutas de Laravel, `@PostMapping` de Spring) | El framework ya trae el punto único de entrada | **Front Controller** |
| 2 | Middleware de autenticación | Middleware de Express / grupo `auth` de Laravel / filtro o interceptor de Spring Security | **Chain of Responsibility** (eslabón de la cadena) |
| 3 | Middleware de negocio ligero (cupo de inscripciones, límite de intentos) | Mismo mecanismo de middleware | **Chain of Responsibility** |
| 4 | Middleware de bitácora | Mismo mecanismo de middleware | **Chain of Responsibility** (registra entrada/salida sin tocar el resto de la cadena) |
| 5 | Controlador `PagoController.pagar()` | Acción del framework que traduce el `Request` HTTP en un comando de aplicación | Frontera **MVC** clásica — aquí no se inventa nada nuevo, solo se traduce |
| 6 | Servicio de aplicación `PagoInscripcionService` | Objeto de dominio propio | Orquestador que usa **Factory** para elegir el cobrador según el método elegido |
| 7 | `MetodoPagoFactory.crear(tipo)` devuelve la Strategy correspondiente | — | **Factory Method / Simple Factory** |
| 8 | `MetodoPago.cobrar(monto)` (tarjeta, SPEI o ventanilla) | — | **Strategy** |
| 9 | Dentro de la Strategy de tarjeta/SPEI, se invoca al banco | Cliente HTTP propio que envuelve al banco | **Adapter** (traduce "crédito"/`00`↔`01` a "pago de inscripción"/`acreditado`↔`rechazado`) |
| 10 | Persistencia del resultado del pago | Transacción del ORM (`DB::transaction`, `@Transactional`, `EntityManager` transaccional) — ya la ofrece el framework | **Unit of Work** (no se escribe a mano) |
| 11 | Tras el commit exitoso, se publica un evento `PagoAcreditado` | Bus de eventos propio o simplemente una lista de listeners que el servicio notifica al final | **Observer / Publicador-Suscriptor** — de aquí cuelgan, ya desacoplados entre sí, el alta en control escolar, el correo y el aviso a caja |
| 12 | Serialización de la respuesta | El mismo controlador, o un Presenter, decide JSON o HTML según el cliente (app vs kiosco) | **Strategy de presentación / View** |

No se agrega, por ejemplo, un "capa de DTO" que solo copie campos de un objeto a otro sin transformarlos, ni un "repositorio" para el evento `PagoAcreditado` si nadie más que los tres suscriptores lo va a leer: eso sería una capa que únicamente delega, y el enunciado pide explícitamente no inventar eso.
